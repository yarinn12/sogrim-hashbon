# iOS keyboard boundary controls after AECB

The actual AECB iOS artifact (`11682088922`, ZIP SHA-256 `c31afb5f7521acf273993ecfbe680fda8ff0ecc4d32493bd6337bc95ffc48ec9`) contains 13 completed phases in each OS category, real trusted UIKit input, acknowledged save, background/resume and rendered restoration after relaunch. The source is `aecb3fe946ca25408b60851f791918e8c5b17c7c`, tree `97d2ca554501ea0db4e8fcd7aa342ca303118297`. Both XCTest journeys passed, but the original artifact acceptance failed. This is not full Native acceptance.

In the default keyboard-name capture, the name field is at 276.625–334.625 and Next at 363–415, above the real keyboard at 449. The system screenshot confirms both controls are fully visible. However, JavaScript reports visualViewport.offsetTop=81, documentScroll.y=81, while the Native contentOffset.y is also 81 and the scroll view starts at zero. The validator therefore maps the visual bottom to 530 instead of 449. The AX capture has offsetTop=0, both scroll offsets zero, and matches 449. Read-only observation of all 1,081 original assert expressions found exactly this one failing expression at prepare.py:163. No other assertion was bypassed for acceptance, and this diagnostic is not a passing acceptance run.

The earlier actual `4e77d12` artifact exposed a separate product bug: the name field was covered by the sticky action footer. XCTest rejected the field's hit target. The product fix and permanent expense-keyboard regression were published in AECB. Artifact acceptance previously checked OS fences but did not explicitly reject partial overlap with the wizard's own header/footer if a center remained hittable.

This QA change strengthens that boundary. The actual journey now records header/footer rectangles plus real DOM hit tests for the field and Next. Acceptance requires the entire field to clear both rectangles and Next to remain inside the footer, retaining the original one-pixel geometry tolerance and every OS/source/font/persistence guard. Four permanent behavioral negative controls cover a covered field edge, covered header edge, covered field center and covered Next center.

The four new controls failed with the unmodified AECB validator (SHA-256 `9f5b8344d3402a4e918e4fee58242ef0231c9da58c1541a6a389245aeabc934c`), because that validator accepted the faults. With the stronger validator, all 30 controls passed. The original validator was loaded from an isolated file using IOS_PARITY_VALIDATOR; product and working-tree source were never replaced. Logs are retained in the root outputs directory as `ios-aec-footer-validator-baseline-red.log` and `ios-aec-footer-validator-green.log`.

The browser suite also exercises the exact journey measurement functions against an actual covering footer: the first fault covers only an edge and keeps the center hittable; the second covers the center; removing the fault restores the original measurement exactly. The fixture uses a real mobile viewport meta tag to avoid Safari's desktop-layout automatic scale. The original exact geometry assertions remain. These are browser/DOM controls without an OS or Capacitor mock, not Native execution. Measurement controls and unchanged journey preflight passed 12/12 across normal and enlarged iPhone WebKit profiles.

For the unresolved Native coordinate discrepancy, later read-only observations are written separately to `native-parity-geometry-keyboard-{amount,name}.json`. They capture frames 0/1/2 after the original screenshot acknowledgement, actual visual offset/pageTop, document/root geometry, keyboard CSS variables, field/header/footer bounds and actual Native state after the observations. They do not replace the sealed original record, postpone trusted actions, relax its mapping gate or turn a first failure into a pass. A subsequent exact-source Native run must establish the cause and pass all strengthened acceptance guards.

No product CSS, font scale, keyboard setting, timeout, retry policy, skip or acceptance tolerance changed here. Physical iPhone verification remains unavailable.

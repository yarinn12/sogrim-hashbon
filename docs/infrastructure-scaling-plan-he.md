# תוכנית תשתית והתרחבות

## החלטה ניהולית

האפליקציה תישאר פשוטה וזולה בשלב ההשקה, אבל כל שירות יקבל תפקיד מוגדר כדי
שנוכל להתרחב בלי שכתוב בהול:

| שכבה | אחריות | מה לא יישמר בה |
| --- | --- | --- |
| אפליקציות Android ו-iOS | הממשק המלא, עבודה מקומית ותור סנכרון | סודות שרת ונתונים של משתמשים אחרים |
| Vercel | קישורים ציבוריים, דפי הזמנה, API קצר וקבצים דרך CDN | עבודות ארוכות או מצב זמני בזיכרון השרת |
| Supabase | Auth, Postgres, RLS, אירועים משותפים, חברים והתראות | קבצים כבדים שאפשר להפיץ דרך CDN |
| Render | שרת התאוששות, ובהמשך workers למשימות רקע | עותק עצמאי ולא מסונכרן של המידע הכספי |
| דומיין עצמאי | כתובת יציבה מעל ספקי האירוח | תלות בשם `vercel.app` או `onrender.com` בתוך האפליקציה |

Supabase הוא מקור האמת היחיד. Vercel ו-Render חייבים להישאר stateless כדי
שאפשר יהיה להוסיף מופעים או להחליף ספק בלי לפצל מידע.

## תמונת מצב נוכחית

- הממשק כבר ארוז בתוך האפליקציות המותקנות ואינו תלוי בהורדת ה-UI מ-Vercel.
- שינוי שלא הסתנכרן נשמר מקומית ונשלח שוב אחרי חזרת החיבור.
- לכל חשבון ולכל אירוע משותף יש snapshot נפרד ב-Supabase.
- השרת ניתן להרצה גם כ-Vercel Function וגם כ-Docker container ב-Render.
- בדיקת הקיבולת המקומית מ-14 באוגוסט 2026 עברה:
  - 50 משתתפים ו-1,000 הוצאות: payload של 0.66MB, חישוב 16.9ms ומיזוג 48.5ms.
  - 50 אירועים ו-2,500 הוצאות: payload של 1.23MB ומיזוג 79.2ms.
  - בדיקת תקרה של 5,000 הוצאות: payload של 2.45MB ומיזוג 136.2ms.

החולשה הידועה היא עריכה מקבילה של אותו אירוע: כל שינוי כותב כרגע את כל
ה-snapshot של האירוע. אלפי אירועים שונים מתפזרים היטב; עשרות אנשים שעורכים
את אותו אירוע באותו רגע עלולים ליצור התנגשויות.

## שלבי התרחבות

### שלב 0 - השקה מבוקרת

- Vercel נשאר שער ציבורי ראשי.
- Render נשאר התאוששות ידנית ואינו מקבל תנועה שגרתית.
- Supabase נשאר מקור האמת היחיד.
- מפעילים rollout מדורג בחנויות ולא משחררים 100% בבת אחת.
- רוכשים דומיין עצמאי לפני הפצה ציבורית רחבה ומעבירים אליו את כל קישורי
  ההזמנה, ה-callbacks והקישורים המשפטיים.
- ממשיכים בדיקת זמינות כל 30 דקות ובדיקת מסע אמיתי לפני כל rollout.

### שלב 1 - משתמשים אמיתיים ראשונים

הדולר הראשון בתשתית יופנה להגנת המידע, לא לשרת נוסף:

1. משדרגים את Supabase כאשר יש מידע כספי אמיתי בהיקף שאסור לאבד, כדי לקבל
   גיבויים יומיים ומשאבי compute בתשלום.
2. משדרגים את Vercel כאשר מד שימוש מרכזי עובר 70%, כאשר פריסה נחסמת, או כאשר
   העומס כבר מייצר הכנסה שמכסה את העלות.
3. משדרגים את Render רק כשנדרש failover מיידי ללא cold start או כשנוספות
   משימות רקע קבועות.

### שלב 2 - צמיחה יציבה

- מעבירים Realtime לערוצי Broadcast פרטיים במקום להסתמך על Postgres Changes
  במקומות בעלי fan-out גבוה.
- מוסיפים workers ב-Render עבור תזכורות, סריקת קבלות, דוחות ופעולות AI.
- כל משימת רקע מקבלת queue, retries מוגבלים ו-idempotency key.
- נכסים כבדים, כולל סרטוני פתיחה ותמונות שיתוף, נשמרים ב-object storage ומופצים
  ב-CDN עם שמות קבצים בעלי גרסה.
- השרת ממשיך להיות stateless ולכן יכול לגדול אופקית ללא שינוי בלוגיקה.

### שלב 3 - אירועים גדולים או עריכה מקבילה

עוברים בהדרגה מ-snapshot מלא למודל מנורמל:

- `events`
- `event_members`
- `expenses`
- `expense_payers`
- `expense_shares`
- `transfers`
- `event_audit_log`

המעבר יתבצע מאחורי feature flag: יצירת schema, backfill חוזר ובטוח, השוואת
תוצאות החישוב, מעבר קריאה, מעבר כתיבה, ורק לאחר תקופת יציבות הסרת הנתיב הישן.
לא מבצעים החלפה חד-פעמית במסד הנתונים החי.

## ספי פעולה מחייבים

| מדד | אזהרה | פעולה |
| --- | --- | --- |
| גודל snapshot | מעל 1.5MB | מעל 2MB מתחילים פיצול לפני הוספת פיצ'רים לאירוע |
| זמן שמירה p95 | מעל 1.5 שניות | מעל 2.5 שניות משפרים query/payload או compute |
| התנגשויות שמירה | מעל 0.5% | מעל 1% בשעה מתחילים מעבר לכתיבה לפי שורה |
| שינויים שלא סונכרנו | מעל דקה | מעל 5 דקות פותחים incident |
| חיבורי DB | 60% מהתקרה | 75%: pooling/שדרוג לפני הגעה ל-90% |
| CPU מסד נתונים | 60% למשך 15 דקות | 75% למשך 15 דקות: query audit ושדרוג לפי הצורך |
| שגיאות API | מעל 0.5% | מעל 1% בחמש דקות: עצירת rollout |
| שימוש ספק אירוח | 70% מההקצאה | 85%: שדרוג או הורדת תעבורה לפני חסימה |

## בדיקות לפני כל קפיצת מדרגה

1. עומס מתבצע רק מול פרויקט staging נפרד, לעולם לא מול מסד הייצור.
2. נבדקים 50, 100 ו-250 לקוחות מקבילים.
3. מתועדים p50, p95, p99, שיעור שגיאות, שיעור התנגשויות, CPU, חיבורים וגודל
   payload.
4. מריצים מסע דו-חשבוני: הזמנה, הצטרפות, הוצאה, סיכום, סימון העברה והתנתקות.
5. מבצעים תרגיל התאוששות: Vercel לא זמין, Render עולה עם אותם secrets והדומיין
   עובר אליו.
6. בודקים שחזור גיבוי ב-staging לפחות פעם ברבעון.

## כללי אבטחה ופרטיות בקנה מידה

- RLS מופעל ונבדק לכל טבלה חשופה.
- הרשאה לאירוע נקבעת לפי חברות באירוע, לא לפי מידע שנשלח מהלקוח.
- `service_role` נשאר רק בצד השרת ולעולם אינו נארז באפליקציה.
- כל פעולה כספית רגישה מקבלת מזהה idempotency כדי שלחיצה כפולה או retry לא
  ייצרו רישום כפול.
- נשמר audit log לשינויי חברות, מנהלים, הוצאות והעברות בלי לשמור מידע מיותר.
- מחיקת חשבון, ייצוא מידע ומדיניות שמירה ממשיכים להיבדק בכל release gate.

## מה לא עושים עכשיו

- לא משלמים על שני שרתים פעילים לפני שיש לכך צורך מדיד.
- לא מעבירים את כל האפליקציה ל-Render רק בגלל מגבלת Vercel זמנית.
- לא מפצלים את המידע בין שני מסדי נתונים.
- לא משכתבים את מודל האירועים לפני שמדדי אמת מצדיקים זאת.
- לא בונים Enterprise מוקדם; שומרים על נתיב מעבר ברור ומבצעים אותו בזמן.

## ההחלטה הבאה

הצעד התשתיתי הבא הוא דומיין עצמאי שמכוון כרגע ל-Vercel וניתן להעברה ל-Render.
לאחר מכן נקים staging נפרד לבדיקת עומס, ונקבע dashboard שבועי למדדים בטבלה
לעיל. מעבר לתוכנית בתשלום יתבצע לפי הספים, לא לפי תחושת בטן.

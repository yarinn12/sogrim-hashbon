# תהליך העבודה הקבוע של סוגרים חשבון

בהכנת פקד בבדיקת דפדפן, הכינו ומדדו בתוך אותה לולאה מוגבלת כדי שגלילה מתחרה לא תשאיר מדידה מיושנת. שמרו את דרישת הגודל, הגבולות הגלויים, יציבות הפריסה ובעלות הפגיעה; אל תשתמשו בלחיצה מאולצת או בהרחבת זמן כדי להסתיר יעד לא נגיש. בקרת תזמון מדומה צריכה להזיז את הפריסה בתוך שלב ההכנה שהיא בודקת, ולשמור גם בקרות שליליות ליעד מכוסה או קטן מדי. הבדילו בין מנגנון ששוחזר בבקרה לבין סיבה שהוכחה בתיעוד המקורי.

## הכנת לחיצה בלי להתחרות בשחזור מיקוד

במסלול חזרה מדיווח לפרטי משתתף, שחזור המיקוד הקיים פותח את details של פעולת הדיווח. תיעוד QA515 מראה שהבדיקה קראה closed, המתינה למרכז יציב, ובינתיים האזור נפתח; לחיצת ההכנה סגרה אותו. הבדיקה ממתינה כעת לפתיחה ולמיקוד בפקד המקורי לפני פתיחת הדיווח מחדש. בדיקות הבקשה הממתינה, הנעילה, ACK, שני הדיווחים המפורשים והכספים נשמרות. אין שינוי בקוד המוצר או בטיפול בדיווח.

בתיעוד אירוע ממתין, scrollIntoViewIfNeeded הותיר יעד מאחורי הניווט הקבוע בטקסט מוגדל. הכנת הבדיקה משתמשת בגלילה רגילה למרכז, ואז בודקת את אותו מרכז, אותם ממדים ואותה בעלות על הפגיעה לפני הלחיצה. אין force, אישור שמירה או מחיקת תור, ואין החלשה של תנאי הפגיעה או זמני ההמתנה.

## בקרת שורה מכוסה שנוספה בזמן בדיקה

חוסם סינתטי שנועד לכסות רק שורה חדשה חייב להישאר מעוגן לאותה שורה בעת גלילה ושינוי פריסה. מלבן fixed שנמדד לפני שינוי גובה החלון יכול להישאר במקום אחר. בקרת ההתקנה משתמשת ב־`installGuideNewRowControl.mjs`: כותב הגלילה המקורי נשמר, הטקסט נוסף פעם אחת, והחוסם נמצא בתוך השורה החדשה. הבדיקה המקורית עדיין מחייבת דחיית הקריאות ופגיעה בחוסם, ונוספה תזוזת חלון מבוקרת לפני הפגיעה האחרונה. רגרסיית המתאם ובדיקת הדפדפן נכשלו על הבקרה הישנה; הבדיקה אינה טענה לכשל בעיצוב חלון ההתקנה עצמו.

בדיקות הניווט בשורש מוגדל והפריים הראשון נוספו במפורש גם לרשימת מסעות הדפדפנים. שינוי רשימת הכיסוי מוסיף את שני הקבצים בלבד, ומשמר את כל המסעות, המכשירים, התנאים, זמני ההמתנה וכלל דחיית flaky הקיימים. אין לתאר ניסיון מקומי שהחזיר No tests found כהרצת תרחישי דפדפן.

## פריסה לפני פריים תצפית

התאמת ניווט לטקסט מוגדל חייבת להיות שלמה בעת רינדור המסך ויצירת הניווט, גם כשפריים תצפית כבר ממתין. תיעוד QA515 המקורי הראה תוויות בגודל28.235px בשורש37.647px, בלי מחלקת שתי השורות; המחלקה והמרווח המדוד הופיעו מאוחר יותר. אין לפתור זאת באמצעות הקטנת גופן, המתנה נוספת בבדיקה או קבלת retry. שומרים את ה־trace המקורי ומבדילים בין זמן התצפית שנרשם בו לבין הסיבה לעיכוב המארח, שלא נמדדה.

רגרסיית הבקר מחזיקה RAF מול הבקר וכותב הפריסה האמיתיים, ובדיקת דפדפן נוספת מחזיקה רק את פריימי הטיפוגרפיה ומודדת אותיות ושטחי מגע. פריימי ResizeObserver נשארים נדחים כדי למנוע לולאה; אירועי רינדור, העדפות, חזרה וטעינת גופן מתאימים את הפריסה מיד. הבנייה המשותפת ל־Native ממשיכה להשתמש באותו קוד ובאותן בדיקות CSS, ללא שינוי לוגיקת כספים, הרשאות, שמירה או SDK.

כל שינוי עובר ענף נפרד, commit שמור, בדיקות, סקירה ומסירה מאותו מקור קוד. תיקוני העיצוב של iOS, Android והאתר ממשיכים להיבנות מאותה גרסה. מספרי הבנייה בחנויות שונים, תוכן העדכון משותף.

מריצים פיתוח, בדיקות ושרת עם Node 24 כפי שמוגדר ב־CI. קובצי package.json ו־package-lock.json מקבעים engines.node ל־24.x: טווח מינימום פתוח גרם ל־Vercel לבחור Node 26 למרות הגדרת הפרויקט ל־24. גם שלבי התלויות וההרצה ב־Dockerfile של שרת הגיבוי משתמשים ב־Node 24. בדיקת deploymentRuntimeContract משווה את הקבצים ואת שלבי Docker לחמשת מסלולי ה־CI והפריסה. שדרוג major ייעשה במפורש עם בדיקות תאימות; אין שינוי בגרסת האפליקציה למשתמשים.

מסלול Health מדווח מזהה commit מאומת של Vercel או Render, בלי להחזיר ערכי סביבה שאינם SHA תקין. בדיקת HTTP מקומית מכסה את שני הספקים ואת אי־חשיפת הערכים הפסולים. דיווח מזהה ו־Health תקין אינם תחליף להשוואת קובצי האפליקציה בפועל; שרת הגיבוי הציבורי ייושר למקור הסופי רק אחרי שערי הקבלה ואישור הפרסום. כשאין Docker זמין, אין לתאר בדיקת חוזה Dockerfile כבניית image שעברה.

בדיקות סדר הטעינה של Android מקמפלות ומריצות את MainActivity האמיתי ב־JVM עם תחליפי מסגרת סינתטיים. לכן נדרש גם JDK 21 לבדיקות הרגילות; CI מגדיר אותו במפורש. בדיקות Native עם Android ו־Capacitor האמיתיים נשארות חובה. ב־Windows, גם בדיקת סגירת תהליך ה־Bash שבבעלות ה־QA רצה בקבוצה סדרתית נפרדת, כדי שתהליכי בדיקה אחרים לא יצרכו את זמן ההמתנה שלה. כל התרחישים, מגבלות הזמן והתוצאה המחייבת של כל קבוצה נשמרים; בדיקת מלאי מאמתת שכל קובץ רץ פעם אחת. תהליך ה־Bash הזמני שבבעלות הבדיקה מקבל ב־Windows עדיפות מעט גבוהה יותר למשך חייו בלבד. זו בדיקה סינתטית של בעלות וסגירת צינורות תקשורת, ולא מדידת ביצועים של מכשיר; אין שינוי בעדיפות תהליכי המוצר או בהגדרות המערכת.

## נקודות שמירה וחזרה

1. מתחילים מעץ Git נקי. שומרים כל יחידת שינוי ב־commit קטן עם הסבר לבעיה ולתוצאה.
2. לפני סבב שינויים ובמסירת עדכון מריצים `npm run release:checkpoint -- --name checkpoint/<שם-ייחודי>`.
3. הכלי יוצר tag מתועד עם commit ו־tree מדויקים, דוחה שינויים לא שמורים ודוחה שם שכבר קיים. שומרים גם במאגר: `git push origin refs/tags/checkpoint/<שם-ייחודי>`.
4. הגרסה שנמסרה כוללת קבלת CI, מספרי בנייה, טביעות החבילות ושיוך לאותו מקור. נקודת שמירה לבדה אינה אישור שהבדיקות עברו.
5. לתיקון שנכשל משתמשים ב־`git revert <commit>` בענף תיקון ומריצים שוב את הבדיקות. אין `reset --hard` או force-push לענף משותף. לעיון בקוד ישן פותחים ענף חדש מה־tag.
6. בחנויות מחזירים קוד קודם באמצעות בנייה חדשה עם מספר גבוה יותר. tag שומר קוד; הוא אינו גיבוי למסד או ביטול לפעולות משתמשים. שינוי מסד מחייב בדיקות נפרדות, תאימות ללקוחות קיימים ודרך חזרה שנבדקה.

## הפרדה בין תצוגה, לוגיקה, נתונים ושרת

| שכבה | מיקום | אחריות |
|---|---|---|
| תצוגה | `src/ui/` ועיצוב CSS | HTML מתוך מודל תצוגה; אין שמירה, בקשות שרת או חישוב עסקי |
| לוגיקה משותפת | `src/domain/` | חישוב, הרשאות ומיזוג טהור; אין תלות בתצוגה או בקבצי האחסון |
| גישה לנתונים | `src/data/` | אחסון מקומי, ענן, תורים ו־ACK; משתמשת בכללי הלוגיקה |
| שרת | `src/server/`, `server.mjs`, `supabase/` | API, אימות, הרשאות ומסד |
| תיאום האפליקציה | `src/app.mjs` | מחבר את השכבות ומנהל פעולות משתמש; מוציאים ממנו רכיבים בהדרגה |

`npm run qa:architecture` מנתח imports אמיתיים באמצעות parser. הבדיקה דוחה תלות UI בשרת/נתונים/לוגיקה, ותלות של לוגיקה ב־UI או באחסון. קוד ישן נשמר באמצעות adapters שמייצאים את אותן פונקציות. ההפרדה אינה מחייבת שירות חדש או חשבון בתשלום.

החילוץ הראשון כולל כרטיס האירוע, זהות מצב טהורה ומיזוג נעיצות אישיות. `src/app.mjs` עדיין כולל תיאום ורכיבי תצוגה נוספים; מחלצים אותם לפי תחום ועם כיסוי התנהגותי, בלי שכתוב כולל בזמן תיקון גרסה.

## סוגי הבדיקות

מסלוליLinux המפעילים את הכנתAPT המוגבלת ל־Ubuntu24 מקבעים את תמונת הריצה ל־ubuntu-24.04. ב־11.11.2026 הכינויubuntu-latest עבר בפועל ל־Ubuntu26.04 והבדיקה עצרה לפני פתיחת הדפדפנים; אין להרחיב את הרשאת שינוי המראות למערכת אחרת כדי לעקוף זאת. בדיקה קבועה מחייבת את התמיכה המוצהרת בכל המסלולים האלה.

מטריצת הדפדפנים השולחניים מחלקת תרחישים עצמאיים באמצעותfullyParallel בין אותם16 חלקים, עם עובד יחיד בכל חלק ובלי שינוי בתקציבי זמן, ניסיונות חוזרים או סף250 התרחישים. כך קובץ בדיקות שלם אינו דוחף חלק אל מעל הסף. קבוצותserial מפורשות נשארותserial. בדיקתIntegration מקומית מריצה את מתכנןPlaywright האמיתי ומשחזרת את חלק9 שחרג ל־251; מאמת האיגוד הקיים ממשיך להוכיח שכל תרחישי המקור נכללו פעם אחת בכל16 החלקים.

ב־Windows אין להפעיל ריצות דפדפן או בניות כבדות במקביל לשלב בדיקות התהליכים שבבעלות ה־QA. החלוקה הסדרתית בתוך npm test אינה מבודדת אותו ממשימות שהופעלו בנפרד. מריצים את הסוויטה הרגילה לבדה, ורק לאחר סיומה מפעילים את מסעות הדפדפן. אם אירעה חריגת זמן בזמן ריצות מקבילות, שומרים את קבלת הכשל, מאבחנים את התרחיש המבודד ומריצים שוב את הסוויטה המלאה ללא העומס; אין להגדיל timeout, להחליש assertion או לתאר את הריצה שנכשלה כעוברת.

בהרצת QA מתוך סביבת Windows שהנתיב הזמני שלה ארוך, מגדירים `TEMP` ו־`TMP` בתהליך הבדיקה בלבד לתיקייה קצרה וייעודית בבעלות המשימה, בתוך שורש עבודה מאושר. בקרות ה־iOS הסינתטיות יוצרות עץ תיקיות המדמה סימולטור; נתיב sandbox ארוך עלול לחרוג ממגבלת הנתיבים של Windows לפני הרצת הבקרות. אין שינוי בהגדרות המערכת או בתקציבי הבדיקה. ה־wrapper הקבוע מפעיל גם את בקרות ה־observer וגם את בקרות כיול ה־host; כישלון של אחת מהן מכשיל את הסוויטה.


- `npm run qa:unit`: כללים ופונקציות, תצוגה ותקינות קוד.
- `npm run qa:integration`: גבולות HTTP/מסד/אחסון/תיאום, עם נתונים סינתטיים בלבד. Inventory מפורש ועוד `*.integration.test.mjs`; אין שינוי במבנה הנתונים הקיים.
- `npm test`: כל הקבצים, כמו לפני ההפרדה. בדיקת inventory מוכיחה שהחלוקה מכסה כל קובץ פעם אחת.
- `npm run qa:e2e`: מסעות מובייל, השוואת דפדפנים וסנכרון שני לקוחות. בדיקות Native, גופנים וטקסט מוגדל נשארות ב־CI.
- כל תיקון תקלה מוכיח OLD נכשל מהסיבה הנכונה ו־FINAL עובר. אין החלשת assertion, דילוג, הארכת timeout או retry שמסתיר כשל.

בדיקות סינתטיות אינן הוכחה לבדיקה על iPhone פיזי, למסירת התראות אמיתית או למצב מסד Production. מציינים זאת בקבלת המסירה.

לפני ריצה שבונה מאגרי Git סינתטיים, אין להעביר לה משתני Git שנקבעו לצורך תיעוד המקור הראשי. שומרים קודם SHA/tree, ומנקים `GIT_WORK_TREE` ו־`GIT_DIR` בסביבת תהליך הבדיקה בלבד. בסבב QA מקומי משתנה כזה הפנה את פקודות ההכנה של שני חוזי Git למאגר אחר והכשיל אותן; זו תקלה בסביבת ההרצה, ולא סיבה לבטל את בדיקות המקור ונקודות השמירה.

## CI/CD ומסירה

בדיקות השיתוף הסגור מפצלות לחיצה אמיתית סביב רענון מבוקר, לאחר בדיקת actionability ללא הפעלה, ומאמתות שה־pointerdown הגיע לכפתור הנכון. בקצה הגלילה דפדפן עשוי להותיר הפרש שברי של פיקסלים. רק פעולות השיתוף לקריאה בלבד רשאיות לשמור את מיקום הקצה הזה, בתוך סף התנועה הקיים, ורק אם הנקודה המקורית עדיין פוגעת באותה פעולה ובאותו אירוע ונתונים. כללי הביטול של פעולות תשלום נשארים בברירת המחדל המחמירה. בדיקות רגרסיה מכסות לחיצה יחידה, כיסוי הנקודה, שינוי רשומה וגלילה שנחסמה; אין שינוי בחישובים, בהרשאות או ב־ACK.

בכפתורי השיתוף אין הקטנת transform בזמן לחיצה: היא שינתה את ממדי הכפתור בין pointerdown לבין החלפתו ברענון. בדיקת גאומטריה אמיתית ובדיקת חילוץ CSS ל־Native מגינות על אותו כלל בשתי המעטפות.

בקרת הכיסוי השלילית במסך ההתקנה משתמשת בשכבה קבועה המכסה את התצוגה גם כשהחלונית זזה או נגללת. מלבן שנמדד פעם אחת סביב טקסט אינו מבטיח שהטקסט יישאר מכוסה. מאמתים פגיעה בשכבת הכיסוי לפני ואחרי בדיקת הקריאות, כולל תזוזה מבוקרת; בדיקת הקריאות עצמה ותנאי הכשל נשמרים.

בקרת התנועה החיובית באותו מסך משתמשת באנימציית דפדפן קצובה של500ms שנראית למחסום האנימציות הקיים. בקרה קודמת השתמשה ב־inline transform ובטיימר JavaScript, שעלול לא להיות מיוצג במחסום הזה; בקרת השהיית callback משחזרת את כשל ה־OLD. בקרה שלילית נפרדת משאירה תנועה מושהית ומחייבת את בדיקת הטרנספורם להיכשל לפני שמחזירים את החלונית למצב יציב. זמני ההמתנה, תנאי הגאומטריה ומדיניות ה־retry נשארים כפי שהיו; אין שינוי בקוד המוצר.

בתצוגת עדכונים ממתינים בבית, קבלת פירוט שגיאה חדש לאירועים שכבר ברשימה מעדכנת את המלל והייחוס במקום. גם הפירוט הפנימי וכפתורי האירועים נשארים מחוברים: החלפתם ביןpointerdown ל־click עלולה לאבד פתיחה או מעבר לאירוע. שינוי אמיתי ביעדי הרשימה בונה את היעדים החדשים; אין שחזור של לחיצה על יעד שהוסר. בדיקות רגילות מאמתות זהות פקדים, ובדיקות דפדפן מזריקות קבלת שגיאה תקינה בזמן לחיצה אמיתית ומאמתות פתיחה, יעד נכון ותור/ACK שלא השתנו. כללי הרשאות, שמירה וכספים נשארים בשכבות הקיימות.

בהכנת נתוני דמה לשרת ה־loopback משתמשים בכלים הקיימיםresetLocalQaStateFresh ו־writeLocalQaStateFresh, או ב־prepareMobileLayoutFixture שמחבר ביניהם. הם פותחים חיבור חדש לכל בקשה ואינם חוזרים על כתיבה אחרי סגירת חיבור. כך נמנע סיכון השימוש בחיבורkeep-alive ישן של כלי הבדיקה; אין שינוי ברשת של המוצר. מאמתים גם את ה־ACK ואת מלוא המטען המקורי, ושגיאת חיבור/HTTP אוACK חסר עוצרת לפני פתיחת העמוד. בדיקתIntegration מפעילה אתbeforeEach האמיתי של מסכי הפלטפורמה מול שרת מבוקר:OLD נופל על חיבור משותף שאינו שמיש, ו־FINAL מתקדם רק אחריreset וכתיבה מאושרת. סגירת החיבור המדויקת בכשלCI המקורי לא נמדדה, ולכן אינה מתוארת כהוכחה מעבר לממצאי הלוג ולתרחיש המבוקר. בתרחישי תמונה/סקריפט מושהים קוראים את מסמךHTML האמיתי בחיבור חדש, משמרים גוף וכותרות אבטחה ומשאירים את חסימות המשאבים ובדיקות מוכנות המסך. נשמרות מגבלות30s המקוריות; איןretry חדש, דילוג או שינוי בתנאי מוצר. מקורות: [Node24—שימוש בחיבור קודם](https://nodejs.org/docs/latest-v24.x/api/http.html#requestreusedsocket), [חיבור חד־פעמי](https://nodejs.org/docs/latest-v24.x/api/http.html#class-httpagent), [תקציבAPIRequestContext](https://playwright.dev/docs/api/class-apirequestcontext).

בדיקתACK המחייבת חשפה גם ארבעה קובצי דמה שבהם רשומותfriendContacts לא כללוid, כולל תוספת חבר בתוך גוף תרחיש אחריbeforeEach תקין. הבדיקות הקודמות התעלמו מתשובתHTTP400 והמשיכו מנתונים בדפדפן. מוסיפים רק מזהי דמה קבועים לאותם אנשי קשר, בלי שינוי במשתתפים, בסכומים או בתרחישי הממשק. בדיקתIntegration מפעילה את ה־setup או את כתיבת התרחיש המקוריים בחמשת המצבים הרלוונטיים ומעבירה אתJSON הנשלח למאמת השרת האמיתי:OLD נדחה ו־FINAL מתקבל. סריקתAST קבועה בודקת גם את רשומות אנשי הקשר המפורשות בכל תרחישי הדפדפנים, כדי שחוסרid נוסף יתגלה בסוויטה הרגילה לפני ריצתUI. מאמת השרת, דרישת ה־ACK וכל תנאי הממשק נשמרים. בקשות שבהן נבדקת במפורש תשובתAPI ממשיכות לבדוק את התשובה ואת קריאת הנתונים מהשרת.

בתרחיש הבית של הצטרפות לאירוע ישן, יוצר האירוע נשאר משתמש אחר ומתווסף לנתוני המשתתפים ולחברות באירוע. שעון ההצטרפות, תאריכי האירועים וסדר התצוגה הנבדק נשמרים. בדיקת המטען האמיתי מול מאמת השרת וסריקה של יוצרי אירועים מפורשים בקובצי הכנת שרת נכשלות לפני התיקון ועוברות אחריו. מטמון דפדפן ישן המוזן במפורש לתרחיש התאוששות נשאר תרחיש נפרד; אין להפוך אותו לנתון שרת תקין ולבטל בכך את בדיקת השחזור.

בנהג בדיקת ההתחברות ל־iOS בודקים קיום חלונית בנפרד באפליקציה וב־SpringBoard לפני חיפוש ארבע תוויות ההסכמה המפורשות. בהיעדר חלונית נחסכים חיפושי כפתורים מיותרים; חלונית שמופיעה אחרי בדיקת הקיום תיבדק בסבב הבא. המוניטור, הלחיצות האמיתיות, בדיקות PKCE/קשירת החשבון/שמירה ושחזור וכל מגבלות הזמן נשארים. זה צמצום שאילתות בנהג, לא הוכחה לפתרון ה־scene-create watchdog שנצפה ב־Auth80. בדיקת Native הקבועה ב־macOS היא מבחן ההכרעה; בדיקות מקומיות ב־Windows אינן מריצות Swift או שירות Safari.

לפני הפעלת סימולטור ב־AuthReturn או ב־Native parity, ממתינים פעם אחת להשלמת סריקת ה־runtime ובניית מטמוני המערכת באמצעות `xcrun simctl runtime dyld_shared_cache update --all`. כשל בפקודה עוצר את המסלול לפני boot ובדיקת XCTest; הפלט נשמר ב־`runtime-cache-preparation.log`. Apple מתעדת פגיעה בביצועים בזמן סריקה ובניית מטמונים והמתנה זו ב־[הערות Xcode 26.4](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_4-release-notes). זו הכנת סביבת הבדיקה, ולא הוכחה למוכנות AX או לפתרון תקלה. אין הארכת זמן לבדיקות, החלפת SDK/מכשיר או retry; הכשלים המקוריים נשמרים וקבלת המקור החדש מחייבת את ארבעת מסלולי ה־CI.

בדיקות iOS קובעות סביבת Mac לפי התרחיש: parity על `macos-26` ‏(ARM), ו־AuthReturn על `macos-26-intel`. אלו מסלולי GitHub רגילים וחינמיים למאגר ציבורי, עם Xcode ‏26.6 ו־iOS Simulator SDK ‏26.5. כל workload נבדק בנפרד עם אותו מקור אפליקציה ואותם תנאים: מסכים, מקלדת ושחזור ב־ARM; חזרה מהתחברות, PKCE יחיד ושחזור ב־Intel. תוצאות הניסוי נשמרות כראיות תאימות, כולל כשלים בסביבות האחרות; ארבעת מסלולי ה־CI וכל משימותיהם עדיין נדרשים על המקור הסופי. גרסת תמונת ה־Mac בפועל נשמרת בכל ריצה לצורך אבחון. מקור התמחור: https://docs.github.com/en/actions/reference/runners/github-hosted-runners .


מסלול ה־Native של Android מאמת בחירה מפורשת של SwANGLE עם SwiftShader,
באמצעות פלט הבחירה וספריות ELF שבאמת ממופות לתהליך שבבעלות הבדיקה. בדיקות
ה־legacy נשארות, ובמיוחד הפלט הישן שבו כתוב SwiftShader ב־adapter אבל הבחירה
היא Lavapipe; הוא אינו אישור למסלול החדש. מקבעים PID וזמן לידה מיד לאחר
ההפעלה, ומשווים מקור אפליקציה, מקור כלי QA, SDK וזהות תהליך לפני המסע ואחריו.
שינוי SDK מחייב סקירת התאימות; אין אישור אוטומטי לגרסת ספק חדשה. נשמרים ASG,
המשאבים, מסעות המוצר, זמני ההמתנה והיסטוריית ANR המקוריים. תוצאת ניסוי
תאימות לבדה אינה אישור מסירה או הוכחה לסיבת תקיעה. שינוי במסלול מחייב סקירת
ניסוי התאימות והפעלת ארבעת מסלולי הקבלה על אותו מקור סופי לפני הפצה.

בדיקות הדפדפנים מתחלקות ל־16 חלקים בהשוואת המנועים ול־8 חלקים לכל פרופיל מובייל, עם worker יחיד בכל חלק ומגבלות הזמן המקוריות. לפני הפעלת הדפדפן נאספת רשימת החלק ונבדק שאינה עולה על 250 תרחישים. רשימות המקור המלאות, התכניות, התוצאות וקבלות SHA/tree/run חייבות להתאחד לכיסוי מלא שבו כל תרחיש מופיע בדיוק פעם אחת. תוצאה חסרה, כפולה, שנכשלה, שעברה רק ב־retry או שמגיעה ממקור אחר חוסמת מסירה. דילוגי תחולה מותרים רק לזהויות הקיימות של מקרי iOS/iPad/מגע שאינם נתמכים בפרופיל המסוים; בדיקות המוצר ותנאי התחולה שלהן אינם משתנים לצורך חלוקת העומס.

GitHub QA מריץ גבולות ארכיטקטורה, Unit ו־Integration ולאחר מכן E2E, סנכרון ומעטפות. ארבע הסוויטות המחייבות הן QA, Windows, מקור גופנים ו־iOS AuthReturn. הקבלה חייבת להתייחס לאותו commit SHA; ריצה ישנה, ניסיון חדש שנכשל, job מדולג או job חסר אינם אישור.

גם הפעלה ידנית של Vercel ושל מסלול TestFlight הרגיל חייבת לעבור `release:verify-ci`: ארבע ריצות push של ראש main, עם שמות ה־jobs המחייבים. פרסום main דרך Git integration חסום בקובץ התצורה. התהליך בונה פעם אחת, יוצר deployment ללא החלפת הדומיין, בודק אותו ומאמת שוב את ראש main ואת ה־CI מיד לפני קידום אותה בנייה.

מסלול ה־intake הפרטי שכבר אושר נשאר נפרד. בדיקת `--candidate-branch <ענף-מדויק>` מקבלת ריצות PR/diagnostic של אותו מועמד ומתייגת את הקבלה כ־candidate-readiness-only; היא אינה הרשאת פרסום. מסלול חתימה או intake פרטי מחייב גם סקירת המקור, הוכחת נכסים/חתימות ובדיקת אפס שיוכים או הפצה אוטומטית לפי ההוראות הקיימות. אין להעביר קבלת מועמד למסלול Production או TestFlight הרגיל.

הפעלת פרסום Production נשארת כבויה עד השלמת תנאי המסירה הקיימים: בדיקות המסד, מקור אחיד לכל הפלטפורמות, הגדרות environment והפרטים הנדרשים לפריסה. `RELEASE_PIPELINE_ENABLED=true` הוא מתג הפעלה תפעולי; אין להפעיל אותו כדי לעקוף תנאי שלא הושלם. סודות מוזנים ישירות בהגדרות GitHub, לא בצ׳אט או בקוד.

בהגדרות GitHub יש להגדיר main מוגן, בקשת מיזוג ובדיקות נדרשות, ו־production עם הגבלת ענף וסקירה. הרשאת המחבר הנוכחי מחזירה403 עבור Branch Protection; אין ראיה שהגדרות הניהול כבר מופעלות. קוד הבדיקות והמסירה ניתן לבדיקה בנפרד, וההגדרה החיה תיבדק לאחר קבלת גישה מתאימה. אין לשנות Render auto-deploy או ליצור מסלול תשלום כחלק מהעבודה.

ב־AuthReturn בונים פעם אחת לפני הפעלת הסימולטור שנוצר לריצה. אחרי הבנייה סוגרים אותו, מאמתים שמצבו Shutdown, מוחקים רק את מצבו המקומי ומפעילים אותו מחדש לפני test-without-building. כך שלב הקומפילציה אינו מתוכנן במקביל למערכת האורחת. בסבב Auth88 נמשכה הבנייה אחרי הפעלת האורח כ־21 דקות; מבחן ההתחברות עצמו עבר, אבל ה־job בוטל במגבלת35 הדקות. עומס משאבים הוא הסבר אפשרי לעיכוב, ולא סיבה שהוכחה במדידה. בדיקה סינתטית מפעילה את שלב ה־Bash המקורי ומדמה אורח פעיל בזמן בנייה: OLD נכשל ו־FINAL עובר; בקרה נוספת עוצרת לפני erase ו־XCTest אם הסגירה לא הושלמה. נשמרים אותו SDK, מכשיר, מטמון runtime, מבחן ההתחברות, PKCE ושחזור החשבון, זמני ההמתנה ומגבלת35 הדקות. הצלחה מקומית אינה מאשרת את משך הבנייה ב־Mac; נדרשות ארבע ריצות הקבלה על המקור החדש.

שרת ההתחברות הסינתטי מפנה את מסלולי custom ו־legacy ל־/auth/callback בשרת loopback של אותו מקור מועמד. רק נתיב HTTP האמיתי של המוצר יוצר את החזרה לסכמת מערכת ההפעלה; כלי הבדיקה אינו ממציא callback מקוצר, verifier או אסימון. בדיקת Integration מפעילה את השרת המקורי ומוכיחה ש־OLD מפנה לאתר הציבורי ו־FINAL מגיע דרך handler המועמד, שומר auth_flow וקוד דמה, כולל כותרות אי־שמירה ודוחה flow כפול. כך מופרדת תלות בגרסה הציבורית מהוכחת חזרת ה־SDK והמערכת עם נתוני דמה. בדיקת תאימות לנתיב הציבורי וקבלת התחברות בחבילת החנות נשארות תנאים נפרדים. ב־Auth89 נרשמה הפניית ספק אך לא החלפת PKCE; תלות ה־fixture הציבורית הוכחה, אך היא לבדה אינה מוכיחה את סיבת הכשל המסוימת ב־SDK. Native parity נכשל בנפרד בהמתנת home כשה־native styles עדיין pending; אין לתאר את בידוד ההתחברות כתיקון לעיכוב הזה או להאריך זמני בדיקה.

שלושת כלי held-home קוראים גם הם את מסמך המקור באמצעות readLocalQaHtmlFresh: בקרת התסריט המושהה, התמונה המושהית ו־readiness-control. ב־QA513 נרשם route.fetch: socket hang up בקריאת הבית של מסך הגדרות האירוע ב־iPad4; בדיקות המשתנה החסר שבאו אחריו היו תוצאה של כשל טעינת הדמה. בדיקת Integration מפעילה כל callback מקורי מול שרת שסוגר חיבור Playwright משותף, ומאמתת שחיבור חדש שומר מסמך, query וכותרות אבטחה ומותיר את המשאב הנוסף חסום עד release. OLD נכשל בשלושת המסלולים; בקרות HTTP503 דורשות עצירה לפני החלפת מסמך במקום המשך עם עמוד שגיאה. FINAL עובר בששת המקרים. נשמרים תקציב30s, ה־CSP, חסימות המשאבים ובדיקת בית נראה לפני DCL; אין retry, הקלת תנאי מוכנות או שינוי במוצר. הסגירה המדויקת ב־CI המקורי לא נמדדה, ולכן תרחיש החיבור המבוקר אינו מוצג כהוכחה לאורכו המקורי. אין החלפה גורפת של route.fetch בבקשות מודולים אחרות.

אותו חוזה קריאה חל גם על שלוש החלפות HTML ישירות: בקרת preflight המושהה, מסמך החזרה לחשבון Google ותרחיש כשל סרטון הפתיחה. הבדיקות מחלצות ב־AST את callbacks המקוריים ומפעילות אותם מול חיבור משותף שנדחה ו־HTTP503; OLD נכשל בששת המקרים ו־FINAL שומר גם את ספירת שני מסמכי הכניסה, את החלפות הגוף המקוריות ואת כותרות האבטחה. אין שינוי בתוכן הציפיות, שמות התרחישים, חלוקת העומס או מדיניות ה־retry. בקשות מבודדות של מודולי JavaScript אינן נכללות בהחלפה הזאת.

## קבלת עדכון

## סקירת עיצוב מסך אחר מסך

עובדים עם המשתמש על עמוד או אזור אחד בכל פעם. לפני מעבר לעמוד הבא מצלמים את המצב הנוכחי, בודקים את כל העמוד ואת המצבים הרלוונטיים שלו, מרכזים הערות ומסיימים את השינויים שסוכמו.

בכל סקירה בודקים מרכוז של הטקסט והסמל הגלויים, מרווחים, RTL, שבירת שורות, טקסט שנחתך, אזורי לחיצה ותוכן שמתחת לניווט הקבוע, ברוחבי מובייל שונים ובטקסט מוגדל. מתעדים מגבלות: בדפדפן מקומי אין הוכחה להתנהגות במכשיר Native פיזי.

מוסיפים תמיד הערכה מנומקת של מראה גנרי או תבניתי: כרטיסים בתוך כרטיסים, הילות וצללים מוגזמים, קישוט ללא תפקיד, מסרים פרסומיים חוזרים וחוסר אחידות ברכיבים. זו ביקורת חזותית, לא קביעה לגבי מקור הקוד. מפרידים בין תקלה מדידה להעדפה עיצובית ומציעים שינוי נקודתי לדיון. שומרים על המותג הירוק, כרטיס הבית וההילה העדינה שאושרו; שינויים רחבים נבחנים עם המשתמש לפני ההטמעה.

## טקסט מוגדל מהגדרות המערכת

בודקים פתיחה כשהגדלת הטקסט כבר פעילה במערכת, לצד העדפת טקסט בתוך האפליקציה. אין להסתפק בשינוי גודל הטקסט של ההורה: מודדים את האותיות שבתוך strong/span, שמות האירועים, תוויות ומספרי המסננים ותוויות הניווט. מכבדים את הגודל המבוקש ומאפשרים לרכיבים להתרחב או לעבור שורה.

בניווט מוגדל, הפריסה נקבעת לפי רוחב המילים הגלוי והמרווח לתוכן נקבע לפי גובה הניווט בפועל. בודקים מסך צר, חזרה לגודל רגיל, סיבוב מסך, מעבר בין מסכים והגעה לפריט האחרון. בדיקת `e2e/system-text-reflow.spec.mjs` מדמה את מדידת גופן המערכת לפני הפתיחה; זו בדיקת דפדפן סינתטית. היא אינה מחליפה בדיקה במכשיר iPhone עם הגדרת הטקסט של המשתמש או בדיקת Native לפני מסירה.


## אימות מראה iOS וגופנים

WebKit ב־Windows מועיל לבדיקות תפקוד, נגישות, שבירת שורות וגאומטריה. הוא אינו אישור למראה הגופנים ב־iOS: בבדיקת QA המקומית התגלתה מגבלת ציור משקלים בגופנים משתנים, גם לאחר טעינת Rubik ו־Inter והגדרת המשקל הנכונה. אין לשנות משקלי מוצר כדי לחקות את התוצאה הזאת ואין להחליש בדיקות כדי לעקוף אותה.

לפני אישור חזותי ל־iOS מצלמים ובודקים בסביבת Apple (WebKit ב־macOS או מכשיר iPhone), כולל טקסט מוגדל. מציינים בנפרד בדיקות דפדפן ב־Windows, אמולציה וחבילת Native. בדיקה מקומית אינה מאשרת APK/IPA, מקלדת פיזית או מסירת Production.

מקור למגבלת המנוע: [Playwright WebKit Windows variable-font issue](https://github.com/microsoft/playwright/issues/16104). יש לתעד מחדש את המגבלה כאשר סביבת הרינדור משתנה, ולא להפוך אותה לדילוג קבוע על בדיקות המוצר.


## חיבור HTTP מבודד ושמירת גלילה אחרי פתיחת מקלדת

בדיקות הדפדפן מפעילות את אותו createAppHandler דרך scripts/qa/serve-browser-qa.mjs על loopback, עם Connection: close. כך מסמך חדש אינו יורש חיבור HTTP מקומי פנוי מהמסמך הקודם. ההכנה מסרבת לסביבת פריסה ולשירותים פרטיים; אינה משנה את server.mjs, את נתוני התשובה, את כללי ההרשאה, את שרת הייצור או את פרוטוקול הנכסים של Native. ב־QA516 נמצא אחרי reload כשל טעינת publicScrollIntentLayer, ואחריו מסך טעינה; שמירת ההוצאה עצמה אומתה לפני כן. בדיקת HTTP מול השרת האמיתי מוכיחה OLD reuse מול FINAL חיבור חדש, עם אותם בתים וכותרות אבטחה ועם רשימת חסימת קבצים פעילה. זו הוכחת מחזור חיי החיבור במתקן, ולא הוכחה לסיבת הכשל הפנימי המסוים ב־WebKit המרוחק. אין retry, התעלמות משגיאה או החלפת תגובת מוצר בנתוני דמה כדי להעביר תרחיש.

תיקון פריסת מקלדת מושהה חייב לכבד גלילה חדשה כלפי מעלה וגם כלפי מטה. אחרת החזרת המיקוד לשדה קודם יכולה להרחיק את כפתור ההמשך שכבר הוצג. רגרסיות מפעילות את הבקר האמיתי במתאם גאומטריה, ובדפדפן מחזיקות רק את הפריים של אותו בקר: OLD נכשל בשני מקרי גלילה מטה וב־WebKit, ו־FINAL שומר את יעד ההמשך ואת חישוב החלוקה. קלט חדש עדיין מחזיר את השדה לתחום הנראה. הבקרה אינה מוסיפה יצירת אירועי מסעדה; היא שומרת תאימות לאירועים ישנים. בבדיקת QA מקומית כל שלב משתמש בעותק environment נפרד, ו־PLAYWRIGHT_JSON_OUTPUT_FILE נקבע רק להרצה המסוימת: רשימת בדיקות אינה רשאית לדרוס דוח של שלב קודם.

ב־QA516 לא נרשמה שורת APT שנדחתה ב־AWS, ועשר דגימות נפרדות ראו רקAzure. האבחון המסונן שנוסף סיפק ב־Fonts109 את השורה המדויקת: http://us-east-2.ec2.archive.ubuntu.com/ubuntu/ עם tab ו־priority:1, באורך58 בתים וב־SHA256 ed8f7f23d335015d9e16540435a9b1afa1adf34ba6222ed6dd975dfc1f7ec118. כעת מותר פרופיל EC2 נפרד של הכתובת הזאת בלבד ושל שתי שורות archive/security המוכרות. אין wildcard לאזורים, ערבוב עננים, החלפת URI, פרוטוקול או trust anchor; משתנים רק שלושת בתֵי העדיפות. השורה הראשונה שוחזרה בדיוק מהאבחון; שתי השורות הנוספות במתקן נלקחו מהפרופיל הקיים, ואין טענה שהקובץ המלא שלAWS נשמר. שלוש בקרותOLD נכשלו ו־75FINAL עברו, כולל סירוב לאזור/פרוטוקול/חשבון/נתיב לא מוכרים ולאוסף מעורב. קבלת הפרופיל במערכתGitHub עדיין נדרשת. תוצאתAuth92 חסרה מצב התחברות סופי; אין לשנותSDK/PKCE או תקציב על בסיס השערה. קריאת פלט האבחון המקורי ב־macOS ופרסומו עדיין תלויה באישור הנפרד שנדרש בבדיקת האישור האוטומטית.


## מדידת כותרות בזמן החלפת תוכן

## תקינות אתחול סימולטור לפני מדידת Native

Auth93 על04630c8a בוטל במגבלת35 דקות. לוג האתחול המקורי הסתיים ב־Status=3, isTerminal=YES וב־Data Migration Failed; למרות זאת התהליך המשיך ל־XCTest. יש לשמור את פלט bootstatus ולבדוק גם את תוכנו לפני מדידת Native: מזהה הסימולטור חייב להתאים למכשיר שנוצר, ובסוף נדרש סימון ההצלחה שנמדד ב־Auth91 — Status=4294967295 עםisTerminal=YES ו־Finished. Status=4 עדיין מציין הכנת יישומי מערכת ואינו הצלחה. שני תהליכיQA שלiOS מפעילים את אותו מאמת, ללא שינוי מכשיר,SDK,OS, מגבלת זמן אוretry. שש בקרותOLD הפעילו את מקטעי ה־workflow האמיתיים עם פקודות דמה והוכיחו המשך אחרי פלט כושל/חלקי/זר; כל14 בקרותFINAL עברו, והלוג המקורי שלAuth91 התקבל בעודAuth93 נדחה. זו הגנה מפני מדידה על אתחול פגום, ולא תיקון מוכח לשורש כשל מיגרציית המערכת בשרתApple. קבלתNative ו־Auth בריצה חדשה עדיין נדרשת. אבחוןAuth92 המקורי בוצע בנפרד לאחר אישור מפורש לפרסום הפלט המסונן; אין שינוי במסד או במוצר במסגרת אבחון זה.


## שתי צורות הצלחה מלאות של bootstatus

ב־QA518 המקורי נכשל המאמת החדש עצמו לפני מדידתNative: הסימולטור כבר סיים אתחול כשהניטור התחיל, ו־simctl החזיר כותרת עםמזהה המכשיר ואת השורה Device already booted, nothing to do. בלבד. ההנחה שלפיה כל הצלחה כוללת רשימתStatus הייתה מחמירה מדי. יש לקבל גם את תגובת שתי השורות המדויקת הזאת, רק לאחר אימות כותרת יחידה ומזהה המכשיר שנוצר. אין לקבל מילהBooted לבדה, פלט חלקי או מעורב, מכשיר זר אוData Migration Failed. מסלולStatus המלא נשאר עםאותו סימוןסיום4294967295/Finished. שתי בקרותOLD הפעילו את ה־workflow האמיתי עםCLI דמה והוכיחו דחייה שגויה של הצלחה; כל22 בקרותFINAL עברו, כולל פלט סותר/חלקי/זר. לוגי המקור שלAuth91 ו־Auth94 ושלNative518 התקבלו, ולוגAuth93 הכושל עדיין נדחה. אין שינוי במוצר,SDK,מכשיר,תקציב אוretry. קבלת כל ארבע הריצות וכל68 המשימות על המקור החדש עדיין נדרשת.


## תצפית מצב רקע ב־XCTest על MainActor

ב־QA519 המקורי עברו אתחול, הקלדה ושמירת הוצאה. אחריHome נרשמה בתוך ה־predicate תצפית אחת בלבד שלמצב4; ההמתנה הסינכרונית הסתיימה בכשל, ובאבחון המאוחר נרשם מצב3 וצולם מסךהבית שלiOS. לא נרשם באיזהactor רץ ה־predicate המקורי ולכן אין טענה להוכחת שורש הכשל או לתיקון מוכח שלמוצר. Apple מתעדת כי XCTNSPredicateExpectation שנבדקת באמצעות await fulfillment(of:timeout:) מוערכת עלmain actor, בניגוד למסלול ההמתנה הסינכרוני. בדיקתNative משתמשת כעת במסלול המתועד, בודקת בזמן ריצהThread.isMainThread וממתינה לאותם מצבי רקע, לאותה הפעלה יחידה, לאותם מונים חדשים ולצילוםresumed. תקציב35 שניות משותף נשמר; relaunch נשאר45. אין קריאתAX בממתין הרקע, sleep/poll חדש,SDK/מכשיר חדש אוretry. ארבע בקרותOLD נכשלו במודלactor מבוקר ובחוזה ההמתנה; כל19FINAL עברו. אלו בקרות מקומיות ולא הרצתSwift/SDK. קבלתNative חדשה עםהמערכת וה־SDK המלאים עדיין נדרשת, כולל טקסט מוגדל. מקור: https://developer.apple.com/documentation/xctest/xctnspredicateexpectation


## מיפוי שדות מול המקלדת ושימור תחומי כיסוי

# תהליך העבודה הקבוע של סוגרים חשבון

כל שינוי עובר ענף נפרד, commit שמור, בדיקות, סקירה ומסירה מאותו מקור קוד. תיקוני העיצוב של iOS, Android והאתר ממשיכים להיבנות מאותה גרסה. מספרי הבנייה בחנויות שונים, תוכן העדכון משותף.

מריצים פיתוח ובדיקות עם Node 24 כפי שמוגדר ב־CI. דרישת המינימום המוצהרת היא Node 20.10.0, התואמת לדגל ויסות תהליכי הבדיקה; אין שינוי בגרסת האפליקציה למשתמשים.

בדיקות סדר הטעינה של Android מקמפלות ומריצות את MainActivity האמיתי ב־JVM עם תחליפי מסגרת סינתטיים. לכן נדרש גם JDK 21 לבדיקות הרגילות; CI מגדיר אותו במפורש. בדיקות Native עם Android ו־Capacitor האמיתיים נשארות חובה. ב־Windows, גם בדיקת סגירת תהליך ה־Bash שבבעלות ה־QA רצה בקבוצה סדרתית נפרדת, כדי שתהליכי בדיקה אחרים לא יצרכו את זמן ההמתנה שלה. כל התרחישים, מגבלות הזמן והתוצאה המחייבת של כל קבוצה נשמרים; בדיקת מלאי מאמתת שכל קובץ רץ פעם אחת. תהליך ה־Bash הזמני שבבעלות הבדיקה מקבל ב־Windows עדיפות מעט גבוהה יותר למשך חייו בלבד. זו בדיקה סינתטית של בעלות וסגירת צינורות תקשורת, ולא מדידת ביצועים של מכשיר; אין שינוי בעדיפות תהליכי המוצר או בהגדרות המערכת.

## נקודות שמירה וחזרה

1. מתחילים מעץ Git נקי. שומרים כל יחידת שינוי ב־commit קטן עם הסבר לבעיה ולתוצאה.
2. לפני סבב שינויים ובמסירת עדכון מריצים `npm run release:checkpoint -- --name checkpoint/<שם-ייחודי>`.
3. הכלי יוצר tag מתועד עם commit ו־tree מדויקים, דוחה שינויים לא שמורים ודוחה שם שכבר קיים. שומרים גם במאגר: `git push origin refs/tags/checkpoint/<שם-ייחודי>`.
4. הגרסה שנמסרה כוללת קבלת CI, מספרי בנייה, טביעות החבילות ושיוך לאותו מקור. נקודת שמירה לבדה אינה אישור שהבדיקות עברו.
5. לתיקון שנכשל משתמשים ב־`git revert <commit>` בענף תיקון ומריצים שוב את הבדיקות. אין `reset --hard` או force-push לענף משותף. לעיון בקוד ישן פותחים ענף חדש מה־tag.
6. בחנויות מחזירים קוד קודם באמצעות בנייה חדשה עם מספר גבוה יותר. tag שומר קוד; הוא אינו גיבוי למסד או ביטול לפעולות משתמשים. שינוי מסד מחייב בדיקות נפרדות, תאימות ללקוחות קיימים ודרך חזרה שנבדקה.

## הפרדה בין תצוגה, לוגיקה, נתונים ושרת

| שכבה | מיקום | אחריות |
|---|---|---|
| תצוגה | `src/ui/` ועיצוב CSS | HTML מתוך מודל תצוגה; אין שמירה, בקשות שרת או חישוב עסקי |
| לוגיקה משותפת | `src/domain/` | חישוב, הרשאות ומיזוג טהור; אין תלות בתצוגה או בקבצי האחסון |
| גישה לנתונים | `src/data/` | אחסון מקומי, ענן, תורים ו־ACK; משתמשת בכללי הלוגיקה |
| שרת | `src/server/`, `server.mjs`, `supabase/` | API, אימות, הרשאות ומסד |
| תיאום האפליקציה | `src/app.mjs` | מחבר את השכבות ומנהל פעולות משתמש; מוציאים ממנו רכיבים בהדרגה |

`npm run qa:architecture` מנתח imports אמיתיים באמצעות parser. הבדיקה דוחה תלות UI בשרת/נתונים/לוגיקה, ותלות של לוגיקה ב־UI או באחסון. קוד ישן נשמר באמצעות adapters שמייצאים את אותן פונקציות. ההפרדה אינה מחייבת שירות חדש או חשבון בתשלום.

החילוץ הראשון כולל כרטיס האירוע, זהות מצב טהורה ומיזוג נעיצות אישיות. `src/app.mjs` עדיין כולל תיאום ורכיבי תצוגה נוספים; מחלצים אותם לפי תחום ועם כיסוי התנהגותי, בלי שכתוב כולל בזמן תיקון גרסה.

## סוגי הבדיקות

ב־Windows אין להפעיל ריצות דפדפן או בניות כבדות במקביל לשלב בדיקות התהליכים שבבעלות ה־QA. החלוקה הסדרתית בתוך npm test אינה מבודדת אותו ממשימות שהופעלו בנפרד. מריצים את הסוויטה הרגילה לבדה, ורק לאחר סיומה מפעילים את מסעות הדפדפן. אם אירעה חריגת זמן בזמן ריצות מקבילות, שומרים את קבלת הכשל, מאבחנים את התרחיש המבודד ומריצים שוב את הסוויטה המלאה ללא העומס; אין להגדיל timeout, להחליש assertion או לתאר את הריצה שנכשלה כעוברת.

בהרצת QA מתוך סביבת Windows שהנתיב הזמני שלה ארוך, מגדירים `TEMP` ו־`TMP` בתהליך הבדיקה בלבד לתיקייה קצרה וייעודית בבעלות המשימה, בתוך שורש עבודה מאושר. בקרות ה־iOS הסינתטיות יוצרות עץ תיקיות המדמה סימולטור; נתיב sandbox ארוך עלול לחרוג ממגבלת הנתיבים של Windows לפני הרצת הבקרות. אין שינוי בהגדרות המערכת או בתקציבי הבדיקה. ה־wrapper הקבוע מפעיל גם את בקרות ה־observer וגם את בקרות כיול ה־host; כישלון של אחת מהן מכשיל את הסוויטה.


- `npm run qa:unit`: כללים ופונקציות, תצוגה ותקינות קוד.
- `npm run qa:integration`: גבולות HTTP/מסד/אחסון/תיאום, עם נתונים סינתטיים בלבד. Inventory מפורש ועוד `*.integration.test.mjs`; אין שינוי במבנה הנתונים הקיים.
- `npm test`: כל הקבצים, כמו לפני ההפרדה. בדיקת inventory מוכיחה שהחלוקה מכסה כל קובץ פעם אחת.
- `npm run qa:e2e`: מסעות מובייל, השוואת דפדפנים וסנכרון שני לקוחות. בדיקות Native, גופנים וטקסט מוגדל נשארות ב־CI.
- כל תיקון תקלה מוכיח OLD נכשל מהסיבה הנכונה ו־FINAL עובר. אין החלשת assertion, דילוג, הארכת timeout או retry שמסתיר כשל.

בדיקות סינתטיות אינן הוכחה לבדיקה על iPhone פיזי, למסירת התראות אמיתית או למצב מסד Production. מציינים זאת בקבלת המסירה.

לפני ריצה שבונה מאגרי Git סינתטיים, אין להעביר לה משתני Git שנקבעו לצורך תיעוד המקור הראשי. שומרים קודם SHA/tree, ומנקים `GIT_WORK_TREE` ו־`GIT_DIR` בסביבת תהליך הבדיקה בלבד. בסבב QA מקומי משתנה כזה הפנה את פקודות ההכנה של שני חוזי Git למאגר אחר והכשיל אותן; זו תקלה בסביבת ההרצה, ולא סיבה לבטל את בדיקות המקור ונקודות השמירה.

## CI/CD ומסירה

בנהג בדיקת ההתחברות ל־iOS בודקים קיום חלונית בנפרד באפליקציה וב־SpringBoard לפני חיפוש ארבע תוויות ההסכמה המפורשות. בהיעדר חלונית נחסכים חיפושי כפתורים מיותרים; חלונית שמופיעה אחרי בדיקת הקיום תיבדק בסבב הבא. המוניטור, הלחיצות האמיתיות, בדיקות PKCE/קשירת החשבון/שמירה ושחזור וכל מגבלות הזמן נשארים. זה צמצום שאילתות בנהג, לא הוכחה לפתרון ה־scene-create watchdog שנצפה ב־Auth80. בדיקת Native הקבועה ב־macOS היא מבחן ההכרעה; בדיקות מקומיות ב־Windows אינן מריצות Swift או שירות Safari.

לפני הפעלת סימולטור ב־AuthReturn או ב־Native parity, ממתינים פעם אחת להשלמת סריקת ה־runtime ובניית מטמוני המערכת באמצעות `xcrun simctl runtime dyld_shared_cache update --all`. כשל בפקודה עוצר את המסלול לפני boot ובדיקת XCTest; הפלט נשמר ב־`runtime-cache-preparation.log`. Apple מתעדת פגיעה בביצועים בזמן סריקה ובניית מטמונים והמתנה זו ב־[הערות Xcode 26.4](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_4-release-notes). זו הכנת סביבת הבדיקה, ולא הוכחה למוכנות AX או לפתרון תקלה. אין הארכת זמן לבדיקות, החלפת SDK/מכשיר או retry; הכשלים המקוריים נשמרים וקבלת המקור החדש מחייבת את ארבעת מסלולי ה־CI.

בדיקות iOS קובעות סביבת Mac לפי התרחיש: parity על `macos-26` ‏(ARM), ו־AuthReturn על `macos-26-intel`. אלו מסלולי GitHub רגילים וחינמיים למאגר ציבורי, עם Xcode ‏26.6 ו־iOS Simulator SDK ‏26.5. כל workload נבדק בנפרד עם אותו מקור אפליקציה ואותם תנאים: מסכים, מקלדת ושחזור ב־ARM; חזרה מהתחברות, PKCE יחיד ושחזור ב־Intel. תוצאות הניסוי נשמרות כראיות תאימות, כולל כשלים בסביבות האחרות; ארבעת מסלולי ה־CI וכל משימותיהם עדיין נדרשים על המקור הסופי. גרסת תמונת ה־Mac בפועל נשמרת בכל ריצה לצורך אבחון. מקור התמחור: https://docs.github.com/en/actions/reference/runners/github-hosted-runners .


מסלול ה־Native של Android מאמת בחירה מפורשת של SwANGLE עם SwiftShader,
באמצעות פלט הבחירה וספריות ELF שבאמת ממופות לתהליך שבבעלות הבדיקה. בדיקות
ה־legacy נשארות, ובמיוחד הפלט הישן שבו כתוב SwiftShader ב־adapter אבל הבחירה
היא Lavapipe; הוא אינו אישור למסלול החדש. מקבעים PID וזמן לידה מיד לאחר
ההפעלה, ומשווים מקור אפליקציה, מקור כלי QA, SDK וזהות תהליך לפני המסע ואחריו.
שינוי SDK מחייב סקירת התאימות; אין אישור אוטומטי לגרסת ספק חדשה. נשמרים ASG,
המשאבים, מסעות המוצר, זמני ההמתנה והיסטוריית ANR המקוריים. תוצאת ניסוי
תאימות לבדה אינה אישור מסירה או הוכחה לסיבת תקיעה. שינוי במסלול מחייב סקירת
ניסוי התאימות והפעלת ארבעת מסלולי הקבלה על אותו מקור סופי לפני הפצה.

בדיקות הדפדפנים מתחלקות ל־16 חלקים בהשוואת המנועים ול־8 חלקים לכל פרופיל מובייל, עם worker יחיד בכל חלק ומגבלות הזמן המקוריות. לפני הפעלת הדפדפן נאספת רשימת החלק ונבדק שאינה עולה על 250 תרחישים. רשימות המקור המלאות, התכניות, התוצאות וקבלות SHA/tree/run חייבות להתאחד לכיסוי מלא שבו כל תרחיש מופיע בדיוק פעם אחת. תוצאה חסרה, כפולה, שנכשלה, שעברה רק ב־retry או שמגיעה ממקור אחר חוסמת מסירה. דילוגי תחולה מותרים רק לזהויות הקיימות של מקרי iOS/iPad/מגע שאינם נתמכים בפרופיל המסוים; בדיקות המוצר ותנאי התחולה שלהן אינם משתנים לצורך חלוקת העומס.

GitHub QA מריץ גבולות ארכיטקטורה, Unit ו־Integration ולאחר מכן E2E, סנכרון ומעטפות. ארבע הסוויטות המחייבות הן QA, Windows, מקור גופנים ו־iOS AuthReturn. הקבלה חייבת להתייחס לאותו commit SHA; ריצה ישנה, ניסיון חדש שנכשל, job מדולג או job חסר אינם אישור.

גם הפעלה ידנית של Vercel ושל מסלול TestFlight הרגיל חייבת לעבור `release:verify-ci`: ארבע ריצות push של ראש main, עם שמות ה־jobs המחייבים. פרסום main דרך Git integration חסום בקובץ התצורה. התהליך בונה פעם אחת, יוצר deployment ללא החלפת הדומיין, בודק אותו ומאמת שוב את ראש main ואת ה־CI מיד לפני קידום אותה בנייה.

מסלול ה־intake הפרטי שכבר אושר נשאר נפרד. בדיקת `--candidate-branch <ענף-מדויק>` מקבלת ריצות PR/diagnostic של אותו מועמד ומתייגת את הקבלה כ־candidate-readiness-only; היא אינה הרשאת פרסום. מסלול חתימה או intake פרטי מחייב גם סקירת המקור, הוכחת נכסים/חתימות ובדיקת אפס שיוכים או הפצה אוטומטית לפי ההוראות הקיימות. אין להעביר קבלת מועמד למסלול Production או TestFlight הרגיל.

הפעלת פרסום Production נשארת כבויה עד השלמת תנאי המסירה הקיימים: בדיקות המסד, מקור אחיד לכל הפלטפורמות, הגדרות environment והפרטים הנדרשים לפריסה. `RELEASE_PIPELINE_ENABLED=true` הוא מתג הפעלה תפעולי; אין להפעיל אותו כדי לעקוף תנאי שלא הושלם. סודות מוזנים ישירות בהגדרות GitHub, לא בצ׳אט או בקוד.

בהגדרות GitHub יש להגדיר main מוגן, בקשת מיזוג ובדיקות נדרשות, ו־production עם הגבלת ענף וסקירה. הרשאת המחבר הנוכחי מחזירה403 עבור Branch Protection; אין ראיה שהגדרות הניהול כבר מופעלות. קוד הבדיקות והמסירה ניתן לבדיקה בנפרד, וההגדרה החיה תיבדק לאחר קבלת גישה מתאימה. אין לשנות Render auto-deploy או ליצור מסלול תשלום כחלק מהעבודה.

## קבלת עדכון

כל מסירה רושמת: SHA/tree, נקודת שמירה, בדיקות ותוצאות כולל כשלים ודילוגי תחולה, גרסאות iOS/Android/PWA, SHA256 של חבילות, מצב החנויות ודרך חזרה. לפני שילוב מסירים קבצים פרטיים וראיות מקומיות מה־diff. כשכמה צ׳אטים עובדים, לכל קובץ משותף יש עורך אחד והראשי מאחד את המקור לפני החתימה.

מקורות: [Git revert](https://git-scm.com/docs/git-revert), [GitHub environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments), [Vercel Git configuration](https://vercel.com/docs/project-configuration/git-configuration).


## סקירת עיצוב מסך אחר מסך

עובדים עם המשתמש על עמוד או אזור אחד בכל פעם. לפני מעבר לעמוד הבא מצלמים את המצב הנוכחי, בודקים את כל העמוד ואת המצבים הרלוונטיים שלו, מרכזים הערות ומסיימים את השינויים שסוכמו.

בכל סקירה בודקים מרכוז של הטקסט והסמל הגלויים, מרווחים, RTL, שבירת שורות, טקסט שנחתך, אזורי לחיצה ותוכן שמתחת לניווט הקבוע, ברוחבי מובייל שונים ובטקסט מוגדל. מתעדים מגבלות: בדפדפן מקומי אין הוכחה להתנהגות במכשיר Native פיזי.

מוסיפים תמיד הערכה מנומקת של מראה גנרי או תבניתי: כרטיסים בתוך כרטיסים, הילות וצללים מוגזמים, קישוט ללא תפקיד, מסרים פרסומיים חוזרים וחוסר אחידות ברכיבים. זו ביקורת חזותית, לא קביעה לגבי מקור הקוד. מפרידים בין תקלה מדידה להעדפה עיצובית ומציעים שינוי נקודתי לדיון. שומרים על המותג הירוק, כרטיס הבית וההילה העדינה שאושרו; שינויים רחבים נבחנים עם המשתמש לפני ההטמעה.

## טקסט מוגדל מהגדרות המערכת

בודקים פתיחה כשהגדלת הטקסט כבר פעילה במערכת, לצד העדפת טקסט בתוך האפליקציה. אין להסתפק בשינוי גודל הטקסט של ההורה: מודדים את האותיות שבתוך strong/span, שמות האירועים, תוויות ומספרי המסננים ותוויות הניווט. מכבדים את הגודל המבוקש ומאפשרים לרכיבים להתרחב או לעבור שורה.

בניווט מוגדל, הפריסה נקבעת לפי רוחב המילים הגלוי והמרווח לתוכן נקבע לפי גובה הניווט בפועל. בודקים מסך צר, חזרה לגודל רגיל, סיבוב מסך, מעבר בין מסכים והגעה לפריט האחרון. בדיקת `e2e/system-text-reflow.spec.mjs` מדמה את מדידת גופן המערכת לפני הפתיחה; זו בדיקת דפדפן סינתטית. היא אינה מחליפה בדיקה במכשיר iPhone עם הגדרת הטקסט של המשתמש או בדיקת Native לפני מסירה.


## אימות מראה iOS וגופנים

WebKit ב־Windows מועיל לבדיקות תפקוד, נגישות, שבירת שורות וגאומטריה. הוא אינו אישור למראה הגופנים ב־iOS: בבדיקת QA המקומית התגלתה מגבלת ציור משקלים בגופנים משתנים, גם לאחר טעינת Rubik ו־Inter והגדרת המשקל הנכונה. אין לשנות משקלי מוצר כדי לחקות את התוצאה הזאת ואין להחליש בדיקות כדי לעקוף אותה.

לפני אישור חזותי ל־iOS מצלמים ובודקים בסביבת Apple (WebKit ב־macOS או מכשיר iPhone), כולל טקסט מוגדל. מציינים בנפרד בדיקות דפדפן ב־Windows, אמולציה וחבילת Native. בדיקה מקומית אינה מאשרת APK/IPA, מקלדת פיזית או מסירת Production.

מקור למגבלת המנוע: [Playwright WebKit Windows variable-font issue](https://github.com/microsoft/playwright/issues/16104). יש לתעד מחדש את המגבלה כאשר סביבת הרינדור משתנה, ולא להפוך אותה לדילוג קבוע על בדיקות המוצר.

# בדיקות קיבולת לפני השקה

הבדיקות מחולקות לשתי שכבות כדי לא לסכן מידע אמיתי.

## 1. בדיקה מקומית ובטוחה

הפקודה הבאה אינה יוצרת תעבורה ברשת:

```powershell
npm.cmd run qa:capacity
```

היא בודקת גודל snapshot, זמני חישוב ומיזוג, וכן 10, 25 ו-50 עורכים
שמתחילים מאותו עותק של אירוע ומוסיפים הוצאות במקביל. הבדיקה נכשלת אם
הוצאה נעלמת, אם המידע הכספי אינו תקין, אם ה-p95 חורג מהתקציב או אם
ה-snapshot עובר את סף שני המגה-בייט.

הדוחות נשמרים תחת `artifacts/performance/` ואינם נכנסים ל-Git.

## 2. בדיקת staging בלבד

הבדיקה הבאה שולחת בקשות GET בלבד לשרת staging ול-Data API של פרויקט
Supabase נפרד. היא אינה כותבת או מוחקת מידע.

```powershell
$env:STAGING_BASE_URL="https://staging.example.com"
$env:ALLOW_STAGING_LOAD_TEST="1"
npm.cmd run qa:staging-load
```

ברירת המחדל היא 100 בקשות לכל יעד עם 25 בקשות מקבילות. ניתן לשנות באמצעות:

- `STAGING_LOAD_REQUESTS` בטווח 1 עד 2,000.
- `STAGING_LOAD_CONCURRENCY` בטווח 1 עד 100.
- `STAGING_LOAD_TIMEOUT_MS` בטווח 1,000 עד 30,000.

הסקריפט מסרב לפעול מול `sogrim-hesbon-app.vercel.app`, מול `APP_PUBLIC_URL`,
מול `PRODUCTION_BASE_URL`, או מול אותו פרויקט Supabase שמוגדר מקומית כייצור.
אם שם המארח אינו כולל `staging`, `stage`, `preview` או `qa`, נדרש גם
`STAGING_CONFIRM_NON_PRODUCTION=1` לאחר בדיקה ידנית.

## תנאי מעבר

- שיעור שגיאות מרבי: 1%.
- p95 מרבי לקריאת staging: 1.5 שניות.
- אין אובדן הוצאות בסימולציית העריכה המקבילית.
- snapshot נתמך נשאר מתחת ל-1.5MB; 2MB הוא סף חירום למעבר למודל מנורמל.

בדיקת GET אינה מחליפה מבחן כתיבות אמיתי. לפני פתיחה לקהל רחב יש להקים
פרויקט Supabase ייעודי ל-staging, להעתיק אליו schema ללא נתוני משתמשים,
ולהריץ מבחן כתיבה מבוקר על אירוע בדיקה בלבד.

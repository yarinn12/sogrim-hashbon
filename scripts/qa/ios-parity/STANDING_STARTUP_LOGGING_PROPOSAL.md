# Standing iOS parity startup logging proposal

This branch starts at `c053989b217740fa9855edfbc2ec83456f498dfc` and instruments only the unsigned `ios-parity-qa` fixture. It does not change the application source or release IPA. `prepare.py` installs `startup-diagnostics.js` at document start, before the existing synthetic service, input trace, and journey scripts. The logger observes existing product performance marks, bounded DOM and resource timing, and reports allowlisted fields through the existing `iosParity` message handler. The native bridge records queued startup events and public WKWebView URL/loading/progress properties. The standing workflow copies the resulting `native-parity-startup-*.log` files with the other native diagnostics.

The logger cannot satisfy readiness, change a test deadline, send a fetch, or mutate the DOM. The native handler accepts only a main-frame diagnostic message and allowlisted stages and fields. URLs, resource names, request bodies, and headers are excluded. Diagnostic send failures are swallowed within the logger so the original QA journey continues.

`journey.js`, `synthetic-service.js`, `ParityUITests.swift`, and `test_validation.py` retain the normalized bytes from `4e6f1df`. The added test pins their normalized SHA-256 values and checks the fixture wiring. The standing validator and XCTest acceptance criteria remain those of the base commit.

Local verification covers logger behavior, resource classification, fixture hashes, and nearby policy and validator tests. A previous logger revision (`8915d5d`) fails the resource regression because it misses a same-host Capacitor asset when the custom-scheme origin is opaque; this branch passes. The iOS simulator and Swift compilation are unavailable in this Windows checkout, so a Mac `ios-parity-qa` run is still needed to confirm generated startup logs in an actual WKWebView session. A passing JavaScript probe cannot establish that WKWebView emits Resource Timing entries on the target runtime.
